1. Step 1 — Data Collection & Loading

Loads 70 real-world driving trip CSV files collected from a BMW i3 electric vehicle with a 60 Ah Lithium-ion battery pack (~1.06M raw instances).

Implementation

  • Module: data_loader.py → load_all_trips(), load_single_trip()
  • File format: Semicolon-delimited (;), Latin-1 encoded

2. Step 2 — Data Preprocessing & Cleaning

Standardizes column headers, fixes character encoding anomalies, removes rows with missing values, and coerces all readings to numeric data.

Implementation

  • Module: data_loader.py → _clean_column_name(), _standardise_columns(), extract_features_target()
  • Column fixes applied:
    • [%) → [%] (mismatched bracket in "max. SoC")
    • ]]] → ] (triple-bracket typo in "Velocity")
    • Leading/trailing whitespace stripped from all column names
    • Unnamed columns dropped entirely
  • Fuzzy matching: ASCII-skeleton matching to handle degree symbol encoding differences (°C vs raw byte)
  • NaN handling: Two-pass approach — first dropna() on selected columns, then pd.to_numeric(errors='coerce') + second dropna()
  • Clean output: Produces 945,026 training instances and 118,974 testing instances (1,064,000 total) with zero remaining missing values.

3. Step 3 — Feature Selection

Selects the 4 primary telemetry measurements as model inputs and manufacturer-estimated State of Charge as target.

Implementation

  • Module: config.py → PAPER_FEATURES, TARGET_SOC

Selected Features

# Feature Units Physical Meaning
1 Battery Voltage V Terminal voltage of the battery pack
2 Battery Current A Instantaneous current (+ve = discharging, −ve = regenerative braking)
3 Battery Temperature °C Internal pack temperature from sensors
4 Ambient Temperature °C External environmental temperature
Target SoC % Manufacturer-estimated State of Charge

Assumptions & Feature Rationale

# Decision / Assumption Justification
1 Baseline 4-Feature Set Adopted by Default Selected directly based on the reference methodology. These represent the primary real-time observables measured by standard EV Battery Management Systems (Voltage, Current, Battery Temp, Ambient Temp).
2 Ground Truth Target is Manufacturer SoC [%] Uses the internal battery pack SoC estimate (SoC [%]) rather than user-facing displayed cluster gauge values, which are damped for human perception.
3 Instantaneous Telemetry (No Feature Engineering in Baseline) Evaluates baseline capability using direct sensor measurements without time-lagged or rolling statistics.

Verification

  • Feature importance analysis (see Step 9) confirms all 4 features contribute to predictions, with Battery Voltage contributing >70% of predictive power.

4. Step 4 — Train/Test Splitting

Partitions the 70 trips into a training set (first 60 trips) and testing set (last 10 trips) using a trip-level partition.

Implementation

  • Module: data_loader.py → prepare_train_test()
  • Split logic: Index-based — trips[0:60] → train, trips[60:70] → test

Split Details

Split Trip Range File Range Instance Count
Training Trips 1–60 TripA01 → TripB28 945,026
Testing Trips 61–70 TripB29 → TripB38 118,974
Total All 70 TripA01 → TripB38 1,064,000

Key Partitioning Rationale

  • Trip-Level Split vs. Random Split: Partitioning strictly by trip (TripA01–TripB28 for training, TripB29–TripB38 for testing) prevents temporal data leakage. A random instance-level split would leak contiguous seconds of telemetry from the same drive cycle into both train and test, producing artificially optimistic metrics.

5. Step 5 — Model Configuration & Hyperparameters

Configures the Random Forest regressor with hyperparameters optimized for noisy battery telemetry, aligning with MATLAB's TreeBagger regression architecture.

Implementation

  • Module: config.py → RF_BASE_PARAMS
  • Library: scikit-learn → RandomForestRegressor

Hyperparameter Configuration

Parameter Value Reasoning
n_estimators 25, 50, 75, 100 4 configurations evaluated; best selected empirically
criterion squared_error Standard MSE-based split criterion for regression
max_features sqrt At each split, only √4 = 2 features are considered. This de-correlates trees and prevents Battery Voltage from dominating every split
min_samples_leaf 5 Each leaf node must contain ≥5 samples. Prevents overfitting to sensor noise and transient current spikes
bootstrap True Each tree trains on a bootstrap sample (sampling with replacement)
n_jobs -1 Use all available CPU cores for parallel tree construction
random_state 42 + run * 100 Different seed per run: 42, 142, 242, 342, 442

Key Modeling Decisions & Architectural Rationale

# Decision / Assumption Justification
1 max_features='sqrt' instead of scikit-learn's default (1.0 = all features) Critical decision. Scikit-learn defaults use ALL features per split, but the reference used MATLAB's TreeBagger which defaults to sqrt. Without this, trees are highly correlated and RMSE degrades to ~6.6%. Setting sqrt brought RMSE down to ~5.89%
2 min_samples_leaf=5 instead of scikit-learn's default (1) MATLAB's TreeBagger regression default is MinLeafSize=5. This regularization prevents deep, overfit trees and smooths predictions for noisy real-world telemetry
3 Unconstrained max_depth Trees grow fully (pruned only by min_samples_leaf). This allows the forest to capture complex non-linear voltage-SOC relationships
The max_features='sqrt' and min_samples_leaf=5 settings were the single most impactful discovery in this project. Initial runs with scikit-learn defaults (max_features=1.0, min_samples_leaf=1) produced RMSE of ~6.65% — far worse than the reference. Switching to MATLAB-equivalent defaults immediately aligned our results with the reference benchmarks (~5.89%).

Validation Strategy & Tree Count Selection

  • Multi-Run Validation (5 Repeats): Instead of relying on a single training run, each tree configuration was trained across 5 independent runs using seeds [42, 142, 242, 342, 442]. This quantifies seed sensitivity and model variance across runs.
  • Empirical Verification of Tree Counts: We evaluated 25, 50, 75, and 100 trees to verify performance ourselves. Results confirmed that 25 trees achieved the lowest RMSE (5.8876%) and MAE (4.3736%), outperforming larger ensembles while training in just 19.9s.
  • Variance Across Runs: Run-to-run variance was minimal (RMSE standard deviation ~0.08–0.10%), confirming that the performance is stable and reproducible.

7. Step 7 — Evaluation Metrics

Evaluates predictions using 4 standard battery regression metrics (RMSE, MAE, MAX Error, and STD DEV), reported in SOC percentage units (%).

Implementation

  • Module: evaluate.py

Metric Definitions

Metric Formula What It Measures
RMSE √[ (1/n) Σ (ytrue − ypred)² ] Overall prediction accuracy (penalizes large errors)
MAE (1/n) Σ |ytrue − ypred| Average absolute deviation (robust to outliers)
MAX Error max( |ytrue − ypred| ) Worst-case single-instance error
STD DEV σ(ytrue − ypred) Spread/consistency of prediction errors
All metrics are in SOC percentage units (%). An RMSE of 5.89% means the model's predictions are, on average, within ~5.89 percentage points of the true SOC value.

9. Step 9 — Visualization Suite

Seven diagnostic plots were generated to provide comprehensive visual analysis of the model's performance.

Plot 1: SOC Estimation Curve (Actual vs. Predicted)

Purpose: Shows how well the RF model tracks the true SOC across all 118,974 test instances. The closer the orange dashed line follows the blue line, the better the model.

What to look for: Tight tracking throughout all driving cycles, including transitions between charging and discharging states.

Plot 2: Prediction Error Profile

Purpose: Visualizes the instantaneous residual error (actual − predicted) across test duration. Ideally, errors should stay close to the zero line.

What to look for: Most errors clustered near 0%, with occasional spikes during rapid SOC transitions (aggressive acceleration/braking).

Plot 3: Feature Importance (Gini / MDI)

Purpose: Ranks the relative predictive contribution of each input feature using Mean Decrease in Impurity (MDI) from the Random Forest.

What to look for: Which sensor readings the model relies on most heavily for SOC predictions.

Plot 4: Tree Count Comparison (Two-Panel RMSE/MAE)

Purpose: Side-by-side comparison of Best and Average RMSE/MAE across all 4 tree configurations with scaled Y-axes to clearly show the differences.

What to look for: 25 trees (leftmost bars) achieving the lowest Best RMSE/MAE. The reference benchmark is shown as a red dashed line.

Implementation note: Y-axes are zoomed in to magnify the small differences between configurations. Without scaling, all bars would appear identical (differences <0.1%).< /p>

Plot 5: Error by SOC Operational Range

Purpose: Evaluates prediction accuracy across discrete battery SOC operational intervals (0–20%, 20–40%, 40–60%, 60–80%, 80–100%) to diagnose non-linear sensitivity across capacity ranges.

What to look for: Left panel highlights binned RMSE/MAE and sample volume (N). Right panel details error dispersion boxplots, confirming consistency across the active operational range.

Plot 6: Error Distribution Histogram

Purpose: Distribution of all prediction errors with mean error and zero-error reference lines.

What to look for: Near-zero mean error (no systematic bias), tight bell-curve shape centered around 0, and long tails quantifying worst-case scenarios.

Plot 7: Per-Trip Performance Breakdown (10 Test Trips)

Purpose: Evaluates individual generalization accuracy across each of the 10 unseen test trips (TripB29 through TripB38), verifying model stability under diverse driving behaviors and environmental conditions.

What to look for: Consistent error bounds across all 10 trips without anomalous failure on individual driving cycles; dashed line displays the ensemble average benchmark.

12. Next Steps & Potential Improvements

The core Random Forest SOC estimation pipeline is complete and matches the reference benchmarks. The following are potential enhancements that could further improve accuracy, robustness, or practical utility:

High Priority

# Enhancement Description Expected Impact
1 Feature Engineering Add derived features: rolling averages (e.g., 10s/30s/60s windows for current/voltage), rate of change (dV/dt, dI/dt), cumulative energy (∫I·dt), and lagged values. These capture temporal dynamics that raw instantaneous values miss. Medium-High: Could reduce RMSE by 0.5–1.5% by capturing temporal patterns in charging/discharging behavior
2 Hyperparameter Optimization Run RandomizedSearchCV or Bayesian optimization over max_features, min_samples_leaf, max_depth, n_estimators (broader range like 10–200) Low-Medium: Current settings are already near-optimal; marginal gains expected (0.05–0.2%)

Medium Priority

# Enhancement Description Expected Impact
3 Baseline Comparison Train a simple Linear Regression or single Decision Tree baseline on the same dataset to quantify how much the Random Forest ensemble improves over a naive approach. Presentational: Strengthens the engineering justification for RF by demonstrating the non-linear advantage

Low Priority

# Enhancement Description Expected Impact
4 Ensemble Stacking Stack the 25-tree RF with a secondary model (e.g., gradient boosted trees) for refined predictions Low-Medium: May squeeze out 0.1–0.3% RMSE but adds complexity
5 Real-Time Inference Demo Build a small demo script that loads the saved .joblib model and runs predictions on a single trip, simulating live BMS deployment Practical: Demonstrates production readiness
6 Temperature-Specific Models Train separate RF models for different ambient temperature ranges (cold <10°C, mild 10–25°C, hot >25°C) Medium: Battery behavior varies significantly with temperature; specialized models could improve accuracy in extreme conditions
